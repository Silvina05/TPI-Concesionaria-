Decisiones de Arquitectura, Diseño y Pedagogía Técnica

Fundamentadas para Coloquio

1. Arquitectura "Diseño vs. Negocio"

Decisión: Se aisló la consola (Diseño) de la capa de Servicio (Negocio). MenuConsola jamás calcula precios, ni lee archivos, ni valida duplicados por sí misma: delega todo a ConcesionariaServicio.

Ventaja: Permite cambiar la interfaz de consola por una ventana Swing o JavaFX sin tocar una sola línea de la lógica de la concesionaria.

2. Coexistencia de List y Map en Servicio

Decisión: El servicio mantiene en paralelo un ArrayList<Vehiculo> y un HashMap<String, Vehiculo> indexado por patente en mayúsculas.

Justificación: El ArrayList preserva el orden y permite clasificaciones dinámicas con Collections.sort(). El HashMap brinda búsqueda instantánea $O(1)$ por patente sin tener que recorrer todo el stock en un bucle.

3. Persistencia con Serialización de Objetos (java 7.pdf)

Decisión: Se utilizó serialización nativa de objetos mediante ObjectOutputStream y ObjectInputStream sobre FileOutputStream y FileInputStream con cierre explícito en finally.

Justificación: Implementa estrictamente la sección de serialización del material oficial (java 7, págs. 14 a 19). Evita algoritmos frágiles de parseo de cadenas o delimitadores que requerían métodos no vistos en clase (como split o Locale). Además, ante un pedido de Live Coding en el coloquio, cualquier nuevo atributo agregado a las clases del modelo se persiste automáticamente sin tocar el archivo de persistencia.

4. Contrato equals() y hashCode() unívoco

Decisión: Dos vehículos son iguales únicamente si coinciden en su patente.

Justificación: Si se incluyeran el precio o el kilometraje en el equals, al cambiar el kilometraje de un usado el objeto dejaría de ser encontrado en las colecciones. La patente es la clave primaria natural del dominio.

5. Uso de Excepciones Comprobadas (Checked)

Decisión: ConcesionariaException hereda de Exception y no de RuntimeException.

Justificación: Según el material java 3, las excepciones comprobadas señalan condiciones que escapan al control inmediato pero que el programa debe anticipar y recuperar. Obliga a la consola a envolver llamadas en try-catch, garantizando robustez absoluta.

6. Repositorio Genérico IRepositorio<T>

Decisión: Se parametrizó el acceso a datos mediante genéricos <T>.

Justificación: Cumple con el Eje 12 ("Uso de Genéricos"). Si el día de mañana se agrega una entidad Cliente o Vendedor, el mismo contrato de repositorio es reutilizable sin duplicar interfaces.

Guía Rápida para el Coloquio Individual: Modificaciones en Vivo

4 Casos Clave de Examen

En el coloquio, los docentes exigirán modificar el código en tiempo real. Aquí tienes los 4 pedidos más frecuentes y cómo resolverlos paso a paso:

1. "Incorpore un nuevo atributo al vehículo"

Ejemplo de consigna: "Agregue el atributo 'tieneAireAcondicionado' a los autos o 'capacidadTanque' a las motos."

Pasos a seguir:

  1. Abrir Auto.java y buscar la sección >>> ZONA DE MODIFICACIÓN EN VIVO <<<.
  2. Declarar el atributo: private Boolean tieneAireAcondicionado;
  3. Añadirlo al constructor y asignar this.tieneAireAcondicionado = ...;
  4. Generar getTieneAireAcondicionado() y setTieneAireAcondicionado().
  5. En mostrarFichaTecnica() añadir la línea de impresión.
// En Auto.java: private Boolean tieneAire; public Boolean getTieneAire() { return tieneAire; } public void setTieneAire(Boolean t) { this.tieneAire = t; }

2. "Modifique o agregue un criterio de filtrado"

Ejemplo de consigna: "Filtre los vehículos por color o unidades usadas con menos de 50.000 km."

Pasos a seguir:

  1. Abrir ConcesionariaServicio.java en la sección de filtrados.
  2. Escribir el método recorriendo listaStock con un bucle for:
public List<Vehiculo> filtrarPorColor(String color) { List<Vehiculo> res = new ArrayList<Vehiculo>(); for (Vehiculo v : this.listaStock) { if (v.getColor().equalsIgnoreCase(color)) { res.add(v); } } return res; }

3. "Agregue una validación personalizada"

Ejemplo de consigna: "No permita registrar unidades con año anterior a 2005 o con precio base menor a 1 millón."

Pasos a seguir:

  1. Abrir ConcesionariaServicio.java y ubicar validarDatosVehiculo().
  2. Agregar el if lanzando DatoInvalidoException:
if (v.getAnio() < 2005) { throw new DatoInvalidoException("No se aceptan unidades anteriores al año 2005."); }

4. "Altere la persistencia o cambie la ruta del archivo"

Ejemplo de consigna: "Guarde el stock en otro archivo o directorio durante la ejecución."

Pasos a seguir:

  1. Abrir RepositorioVehiculosArchivo.java.
  2. Modificar la constante estática superior:
// Para cambiar ruta o nombre de archivo: public static final String RUTA_ARCHIVO_DEFECTO = "data/mi_nuevo_stock.dat";

Defensa conceptual en el coloquio: Si el docente pregunta cómo se guardan los objetos, explica que se utiliza ObjectOutputStream.writeObject() y ObjectInputStream.readObject() según java 7 (págs. 14-19), requiriendo que la clase implemente la interfaz marcadora Serializable.

Casos Reales de Errores e Inexactitudes Auditados:

Incompatibilidad en Persistencia: Uso de APIs Fuera de Programa

La IAG inicialmente propuso una persistencia manual de texto plano con split(";"), Locale.US y String.format(). El alumno auditó el material de la cátedra, detectando que dichas clases y métodos no formaban parte del temario oficial y hacían frágil el Live Coding. Se instruyó a la IAG a reemplazarlo estrictamente por Serialización de Objetos con ObjectInputStream y ObjectOutputStream (java 7.pdf, págs. 14 a 19), reduciendo el código y garantizando persistencia automática ante cualquier nuevo atributo.

Fallo Sintáctico: Comparación de Tipo Primitivo con null

La IAG generó: if (v.getPrecioBase() == null). Como getPrecioBase() retorna el tipo primitivo double, el compilador rechazó la operación (un primitivo vive en el stack y jamás puede ser null). El alumno corrigió la verificación a if (v.getPrecioBase() <= 0), reservando la comparación con null para referencias a objetos.

Sesgo Conceptual: Sobreescritura Excesiva en equals() y hashCode()

La IAG pretendía comparar color y precio para determinar igualdad. En el dominio automotor, dos unidades son la misma únicamente si coincide su Patente. Incluir atributos mutables rompía el contrato de colecciones. El alumno refactorizó equals() y hashCode() para evaluar unívocamente la patente en mayúsculas (java 5.pdf).

Reflexión Crítica del Proceso de Aprendizaje (Pros & Contras):

Pros: La IAG acelera drásticamente la escritura de código repetitivo (getters, setters, constructores y menús de opciones), permitiendo al estudiante focalizarse en la arquitectura de alto nivel.

Contras: Requiere una auditoría técnica permanente por parte del desarrollador. Si no se comprende la diferencia entre tipos primitivos y Wrappers o el contrato de colecciones, el programador queda expuesto ante los requerimientos de Live Coding en el coloquio.
